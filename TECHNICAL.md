# Техническая документация (TECHNICAL)

Этот файл описывает архитектуру, ключевые решения и **процесс разработки**
проекта Form Find & Replace. Пользовательская инструкция — в `README.md`,
журнал изменений — в `CHANGELOG.md`.

## Обзор

Браузерное расширение на Manifest V3. Не требует сборки и внешних зависимостей:
чистые HTML, CSS, JavaScript (в одном JS-файле на слой).

```
form-replace-ext/
├── manifest.json     # Манифест MV3: имя, версия, права, входные точки
├── popup.html        # Разметка интерфейса попапа
├── popup.css         # Стили попапа
├── popup.js          # Логика попапа: состояние правил, рендер, отправка
├── content.js        # Content script: сканирование полей и подмена значений
├── background.js     # Служебный воркер (пустой по требованию MV3)
├── icons/            # Иконки расширения (16/32/48/128 пнг)
├── CHANGELOG.md      # Журнал изменений
└── README.md         # Пользовательская инструкция
```

## Поток данных

1. Пользователь управляет правилами в попапе (`popup.js`).
2. Правила читаются из и пишутся в `chrome.storage.local` (ключ `kfRules`).
3. По действиям пользователя попап запрашивает активную вкладку через
   `chrome.tabs.query` и шлёт через `chrome.tabs.sendMessage` одно из сообщений:
   - `{ type: "KF_FIND", rules }` — поиск, ответ `{ ok, results }`;
   - `{ type: "KF_REPLACE", rules, targets? }` — замена, ответ `{ ok, changed }`.
     `targets` — массив `[{ rule, field }]` (индексы правила и поля из последнего
     поиска); если передан — заменяются только указанные поля, иначе — всё;
   - `{ type: "KF_UNDO", undoAll? }` — отмена замены: без `undoAll` отменяется
     последний заменённый пункт, с `undoAll: true` — все внесённые замены;
     ответ `{ ok, changed }`;
   - `{ type: "KF_SHOW", field }` — прокрутка и подсветка поля на странице.
4. `content.js` слушает сообщения через `chrome.runtime.onMessage`
   и отвечает `{ ok, ... }`.
5. Попап выводит результат.

Если `chrome.tabs.sendMessage` падает (страница открыта до установки/обновления
расширения, content script в ней отсутствует), попап внедряет `content.js`
через `chrome.scripting.executeScript({ target: { tabId }, files: ["content.js"] })`
и повторяет отправку сообщения. Это избавляет от ручной перезагрузки страницы.

## Ключевые решения и модули

### manifest.json
- `permissions`: `activeTab` (доступ к активной вкладке), `storage`
  (сохранение правил).
- `content_scripts.matches: ["<all_urls>"]` — инъекция content script на
  все страницы. Это даёт единое предупреждение о правах при установке.
- `icons` и `action.default_icon` — набор PNG (16/32/48/128) для страницы
  расширений, тулбара и упаковки. Иконки генерируются скриптом
  `generate_icon.ps1` (вне репозитория) и лежат в `icons/`.
- `version` — по Semantic Versioning; это единственное обязательное место
  для версии (браузер использует его для обновлений).

### popup.js
Хранит массив правил в памяти (`rules`), дублируя его в `storage`.
Каждое правило — объект:

```js
{
  find: "текст для поиска",
  replace: "чем заменить",
  mode: "part|exact",
  enabled: true,
  caseSensitive: true
}
```

- `mode: "part"` — замена подстроки во всех вхождениях.
- `mode: "exact"` — полная замена значения при точном совпадении.
- `caseSensitive: false` — регистр игнорируется (для `mode: "part"` regex
  использует флаг `i`, для `mode: "exact"` — сравнение через `toUpperCase()`).
  Любое другое значение, включая отсутствие поля у старых правил, — регистр
  учитывается.
- UI пересоздаётся целиком функцией `render()` (DOM-строительство без
  внешних библиотек), поэтому проектируется так, чтобы события привязывались
  к элементам после их создания.
- В шапке результатов — чекбокс **«Выбрать все»** (`selectAllCb`), который
  помечает все пункты `selectionPlan` разом; состояние поддерживается функцией
  `syncSelectAll()` (снимается, если пользователь снял хотя бы одну отметку).
- Каждый пункт `selectionPlan` — объект `{ resultIndex, field, replace, matched,
  replaced, cb, matchEl, btn }` со ссылками на DOM. `markReplaced(p)` после замены
  заменяет найденный фрагмент на **зелёный** `b.replaced` (`matchCase`) и
  блокирует чекбокс и кнопку пункта.
- Кнопки в футере: **«Заменить выбранные»** (активна, только если отмечен хотя
  бы один ещё не заменённый пункт) и **«Заменить все»** (без выбора). Обе через
  `performReplace(entries)` шлют `KF_REPLACE` с `targets`; `updateReplaceLabel()`
  пересчитывает активность обеих кнопок (незаменённые пункты).
- Кнопка **«Отменить»** (`↺`) открывает всплывающее меню (`undoMenu`):
  «Отменить последнюю замену» → `KF_UNDO` без `undoAll`, «Отменить всё» →
  `KF_UNDO` с `undoAll: true`. Меню закрывается по клику вне `.undo-wrap`.
- Строки списков (`contenteditable` c `ol`/`ul`): при найденных значениях минимум
  в двух строках `content.js` отдаёт **групповой** пункт `{ group: true, rows }`,
  попап рисует его одним блоком (`renderGroup`) — подсказка «Найдено в разных
  строках одного списка», кнопка **«Выбрать для замены»** раскрывает построчные
  чекбоксы, кнопка **«Заменить»** с `targets[].rows` заменяет выбранные строки
  (без выбора — все строки). `unmarkGroup`/`unmarkReplaced` возвращают отображение
  к состоянию «найдено» после отмены.
- Блок списка **разворачивается** кликом по сводке или «Выбрать для замены»;
  клик по строке списка показывает поле на странице (`onShowField`). Отмеченные
  строки развёрнутых списков учитываются в «Заменить выбранные».

### content.js
- Селектор `SELECTOR` охватывает редактируемые `input` (исключены служебные и
  нередактируемые типы: hidden, submit, button, reset, file, checkbox, radio,
  image, color, range), `textarea`, `select` и любые `[contenteditable]`
  (значения `true`, `plaintext-only`, пустое и т.п.).
- `escapeRegExp()` экранирует спецсимволы, чтобы строка поиска трактовалась
  буквально.
- `matchCase(found, replacement)` подгоняет регистр подстановки под регистр
  найденного фрагмента: `JOHN` → прописными, `John` → с заглавной, `john` — как в
  правиле. Так при замене сохраняется написанный в поле регистр слова.
- `setFieldValue()` + `commitChanges()` обновляют значение и эмитят
  `input`/`change` с `bubbles: true` — фреймворки (React, Vue и др.) видят
  изменение.
- Для `contenteditable` замена выполняется по текстовым узлам
  (`replaceInContentEditable` через TreeWalker): велится только текст внутри
  узлов, а HTML-разметка (списки, жирный текст, стили) сохраняется. Ограничение:
  вхождение, разбитое между соседними узлами (например `ap` в `<b>ap</b>ple`),
  не заменяется.
- `applyRules(rules, targets)`: при переданных `targets` изменяются только
  указанные пары «правило → поле»; без `targets` каждое поле обрабатывается
  только первым подходящим правилом (`break`), избегая каскадных перезаписей.
  Перед изменением каждого поля сохраняется его снимок (`captureField`): для
  `input`/`textarea`/`select` — прежнее `value`, для `contenteditable` — `innerHTML`
  (чтобы откат вернул и разметку). Снимки изменённых полей кладутся в **плоский**
  стек отмены `undoStack` (лимит — `MAX_UNDO`, 100 записей).
- `KF_UNDO` → `undoLastRecs()` / `undoAllRecs()`: первая отменяет последний
  изменённый пункт (одно поле), вторая — все снимки из `undoStack`;
  `undoField` возвращает поле к сохранённому состоянию и эмитит `input`/`change`.
  Пустой стек возвращает
  `changed: 0` (попап показывает «Нечего отменять»). Ответ `KF_UNDO` содержит
  `fields` — индексы восстановленных полей; попап по ним откатывает отображение
  найденных значений (`unmarkReplaced`/`unmarkGroup`).
- `matchRule()` считает совпадения и возвращает **пункты по полям**
  (`{ field, text, matched }`), где `matched` — найденный фрагмент в его исходном
  регистре; лимит — `MAX_RESULTS` (50) на правило. Индексы `field` стабильны
  между `KF_FIND` и `KF_REPLACE`, пока DOM не менялся пользователем.
- Если `contenteditable` содержит список (`ol`/`ul`) и `find` найден минимум в
  двух строках, вместо обычного пункта `matchRule` отдаёт групповой
  `{ field, group: true, rows: [{ row, text, matched }] }`, где `row` — индекс
  строки (`listRows`, порядок `li` в документе). Индексы `row` стабильны между
  поиском и заменой, пока DOM не менялся.
- Замена конкретных строк: `targets[].rows` (массив индексов `li`) —
  `applyListRows`/`applyRow` заменяют только выбранные строки через
  `replaceInContentEditable`, сохраняя разметку; без `rows` поле обрабатывается
  целиком (`applyRule`).
- `KF_SHOW` прокручивает и подсвечивает поле оранжевой рамкой
  (`scrollIntoView` + временный `outline`).
- Подсветка на странице (`markMatches`): по `KF_FIND` первые подходящие правила
  помечают поля **оранжевым** фоном. В `contenteditable` найденные фрагменты
  оборачиваются в тег со стилем `background-color: #ffcf8f` по текстовым узлам
  (`wrapRange` через `splitText`; `MARK_BG = #ffcf8f`), для `input`/`textarea`/`select` и точного
  совпадения красится всё поле (`markElement`). `clearMarks()` возвращает исходное
  состояние (обратная замена спанов на текст и сброс фона) и вызывается в начале
  нового `KF_FIND`/`KF_REPLACE`.
- После основного документа расширение проходит по `iframe` того же домена
  через `iframe.contentDocument`; кросс-доменные пропускаются через
  `try/catch` (доступ закрыт политикой безопасности).

## Совместимость с Яндекс.Браузером

Яндекс.Браузер построен на движке Chromium и поддерживает расширения Manifest V3.
Расширение использует только общие для Chromium API (`chrome.storage`,
`chrome.tabs`, `chrome.scripting`, content scripts, service worker) и не зависит
от API, специфичных для Chrome (*chrome.identity* и т.п.), поэтому отдельная его
версия/портирование под Яндекс не требуются.

Установка и обновление распакованного расширения выполняются через
`browser://extensions` с включённым «Режимом разработчика» (подробно — в
`README.md`). Проверяется на тех же ручных сценариях, что и для Chrome.

## Тестирование вручную

1. Установи распакованное расширение (см. `README.md`).
2. Подготовь тестовую страницу с полями (input, textarea, select,
   contenteditable, в т.ч. с нумерованным списком внутри).
3. Создай правило «часть значения» и проверь замену подстроки.
4. Нажми «Найти»: счёт с/без регистра, режим, список пунктов по полям; найденный
   фрагмент выделен жирным оранжевым; «Заменить выбранные» недоступна (ничего не
   отмечено), «Заменить все» активна.
5. Клик по значению пункта — поле прокручивается к центру и подсвечивается
   оранжевой рамкой.
6. Кнопкой «Заменить» у пункта заменяется только это поле; значение становится
   зелёным жирным, кнопка и чекбокс пункта блокируются.
7. Отметь галочками несколько пунктов и нажми «Заменить выбранные» — заменяются
   только отмеченные (и зелёные). Без отметок кнопка неактивна.
7а. Нажми «Заменить все» — заменяются сразу все незаменённые пункты независимо
   от галочек.
8. Проверь сохранение регистра: поле `JOHN`/`John`/`john` при одной паре найдите →
   получает замену прописную/заглавную/как в правиле.
9. В contenteditable с нумерованным списком замени подстроку — список и его
   нумерация сохраняются.
10. После «Найти» проверь оранжевую подсветку: в contenteditable горят найденные
    фрагменты, в input/textarea — поле целиком; после «Заменить» подсветка исчезает.
11. После любой замены (по пункту/отмеченным/всем) новое значение в попапе стало
    зелёным жирным, кнопка пункта заблокирована.
12. Проверь признак «Учитывать регистр» (по умолчанию снят) и точное совпадение.
13. Убедись, что изменения применяются в `textarea`, `select` и в `iframe`
    того же домена.
14. Перезагрузи браузер и убедись, что правила сохранились.
15. «Выбрать все» отмечает сразу все пункты; сняв одну галочку, убедись, что
    «Выбрать все» тоже снимается.
16. Меню «Отменить» (`↺`): «Отменить последнюю замену» возвращает один последний
    пункт, «Отменить всё» — все замены (включая разметку `contenteditable`);
    при пустой истории — «Нечего отменять».
17. «Очистить все» удаляет правила и полностью очищает результаты.
18. На contenteditable со списком из нескольких строк, где `find` есть в каждой
    строке (например `Scala` в трёх `<li>`): «Найти» → один общий блок с
    подсказкой «Найдено в разных строках одного списка». Без нажатия
    «Выбрать для замены» кнопка «Заменить» меняет все строки; после раскрытия и
    отметки части строк — заменяются только они. Найденное в списке — фиолетовое,
    клик по строке показывает поле на странице, сводка раскрывает значения.
19. После «Отменить последнюю замену» значение группы/пункта в списке снова
    отображается как найденное (оранжевым/фиолетовым), чекбоксы и кнопки активны.
20. Отметь строки в развёрнутом списке — счётчик «Заменить выбранные (N)» учтёт
    их вместе с обычными пунктами; замена применится только к отмеченным.

## Процесс разработки

Этот раздел обязателен к соблюдению.

**После каждого изменения кода или документации:**

1. Обнови файлы со старым состоянием (тот же коммит/изменение), если изменение
   их затрагивает.
2. Добавь запись в `CHANGELOG.md`:
   - незавершенную работу — под заголовком `## [Unreleased]`;
   - готовую — в блок конкретной версии `## [x.y.z]`.
   Укажи дату (ISO `YYYY-MM-DD`) и тип записи (Added / Changed / Fixed / ...).
3. Внеси/обнови соответствующее описание в этом файле (`TECHNICAL.md`),
   если изменилась архитектура, поток данных, соглашения или зависимости.
4. Обнови пользовательскую инструкцию `README.md`, если поменялось поведение,
   интерфейс или шаги установки.
5. При выпуске повысь `version` в `manifest.json` согласно Semantic Versioning:
   - **major** — несовместимые изменения;
   - **minor** — новая функциональность (обратно совместимая);
   - **patch** — исправления и незначительные изменения.
   Перенеси записи из `[Unreleased]` в блок новой версии. Версия в `manifest.json`
   и в `CHANGELOG.md` должна совпадать.

### Правило обновления документации
- `README.md` — для пользователя: что делает расширение и как им пользоваться.
- `TECHNICAL.md` — для разработчика: как оно устроено и как менять.
- `CHANGELOG.md` — журнал: что именно поменялось между версиями.

Изменение, не отражённое в этих файлах, считается незавершённым.
